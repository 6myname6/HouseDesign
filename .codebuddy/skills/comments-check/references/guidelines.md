# 注释规范（comments-check 参考）

本文件定义 HouseDesign 项目的注释标准，供 `comments-check` 技能在审查与修复时遵循。
三项核心要求：

1. **完整性 & 占比**：每个函数/方法、每个重要字段都应有注释；注释行占总代码量（注释+代码）≥ 30%，代码 ≤ 70%。
2. **一致性**：注释内容必须与对应代码行为匹配，不夸大、不遗漏、不矛盾。
3. **可读性**：注释应通顺、易懂、长度适中，避免过长行、无意义短语、全大写刷屏、乱码。

---

## 一、注释占比 30 / 70

- 统计口径：注释行（整行 `//`、`/* */` 块内行、行尾 `//`）与代码行之和，空行不计入分母。
- 目标：注释行 / (注释行 + 代码行) ≥ 30%。
- 低于 30% → 视为"注释不足"，需补注释；显著高于 40% 且多为废话注释 → 提示精简。
- 提升占比的正确方式：为函数/字段补**有价值**的注释，而非堆砌无意义行。

## 二、哪些地方必须有注释

### 后端 Java
- 每个 `public`/`private` 方法：用 `/** ... */` Javadoc，说明用途、参数、返回值、抛出的异常。
- 每个类级字段（尤其 `service`/`repository` 注入、配置项、状态标志）：用 `//` 或 `/** */` 说明含义与单位。
- 复杂分支、业务规则、魔法数字：行内或块注释解释"为什么"。

### 前端 Vue / JS
- 每个 `function`、箭头函数、组件 `methods`/`computed`：说明作用。
- Composition API 中每个 `ref`/`reactive` 重要字段（状态、配置、阈值）：说明含义。
- `props`、`emits`、`store` 字段：说明用途与类型约束。
- 模板中非常规结构可用 `<!-- -->` 简要说明。

## 三、一致性（注释 ↔ 代码）

好的注释应做到：
- 描述"做什么 + 为什么"，而非逐行复述"怎么做"（代码本身已表达怎么做）。
- 不出现代码中不存在的符号/函数名（避免复制粘贴导致的描述错位）。
- 不写占位注释：`TODO`/`FIXME`/`待补充`/`待完善` 仅允许作为临时标记，正式代码应消除。
- 参数名、返回值、异常与代码签名保持一致。

**AI 语义复核要点**（脚本只能做启发式，最终判定靠理解）：
- 注释声称的行为，代码是否真的实现了？
- 注释遗漏了关键副作用（如修改了全局状态、发了请求、加了锁）？
- 注释是否过时（代码已改，注释未改）？

## 四、可读性

- 单行注释建议 ≤ 120 字符；超长应换行或改文档注释。
- 避免无意义短语：`// x`、`// tmp`、`// 处理`、`清旧` 这类过短注释应补全。
- 避免全大写刷屏（`ERROR CODE XXX YYY`），正常句式即可。
- 使用中文或英文一致表述，避免中英混杂导致的歧义；专有名词保留英文。
- 注释应面向"读者半年后能否看懂"，而非仅当下。

## 五、好 / 坏 示例

坏：
```java
// 保存
public void save(Project p){ ... }
private int n; // 数量
```

好：
```java
/**
 * 保存设计方案。若项目已存在则覆盖，否则新建。
 * @param p 待保存的项目实体（id 为空时视为新建）
 * @throws BusinessException 当必填字段缺失时
 */
public void save(Project p) throws BusinessException { ... }

/** 当前用户未读数，单位：条 */
private int unreadCount;
```
