# comments-check 注释质量检查

对代码进行三类注释检查，对应三项要求：

1. **完整性 & 占比**：每个函数/重要字段应有注释；注释行占总代码量（注释+代码）≥ 30%，代码 ≤ 70%。
2. **一致性**：注释内容应与对应代码行为匹配（占位、引用不存在的符号、过时/矛盾等）。
3. **可读性**：注释应通顺易懂，无过长行、无意义短语、全大写刷屏、乱码。

## 何时使用

用户提到"注释检查 / 注释缺失 / 注释占比 30/70 / 注释与代码是否一致 / 注释可读性 / 补注释"，
或希望按规范审查、补齐某文件/模块的注释时。

## 工作流

### 1. 运行检查器（机械层面，确定性）

执行内置脚本，得到量化指标与可疑点清单，并生成报告：

```powershell
python .codebuddy/skills/comments-check/scripts/check_comments.py 目标路径... --ratio 0.30 --json JSON路径 --html HTML路径
```

- 目标路径可为文件或目录（目录会递归扫描 `.java/.js/.ts/.vue`，自动跳过 `node_modules/target/dist/build`）。
- 不传路径则扫描当前目录；为本项目检查可传 `backend/src frontend/src`。
- `--ratio 0.30`：注释占比目标下限（默认即 0.30）。
- 输出：控制台摘要 + 各文件占比表 + 重点问题清单；`--html` 生成可点击的彩色报告，`--json` 供程序消费。

脚本负责的三类机械检测：
- 占比：`low_ratio`（低于 30% 标 FAIL）。
- 缺失：函数/方法 `missing_comment_function`（error）、重要字段 `missing_comment_field`（warning）。
- 一致性/可读性启发式：`placeholder`（TODO/待补充等）、`undefined_ref`（注释提及代码中不存在的符号）、`too_short`（无意义短注释）、`too_long`（超过 120 字符）、`all_caps`（全大写刷屏）。

### 2. AI 语义复核（脚本无法判定的部分）

脚本的 `missing`/`placeholder`/`undefined_ref` 是启发式，可能有误报；且**"注释是否真的与代码匹配""是否真正易懂"必须由理解判定**。因此：

- 读取脚本输出的重点问题（尤其 `missing_comment_*`、`placeholder`、`undefined_ref`），逐个打开对应文件位置。
- 对照 `references/guidelines.md` 的标准，判断：
  - 该函数/字段是否真的需要注释（如纯 getter、明显局部变量可放宽）。
  - 注释描述的行为代码是否真的实现（一致性）。
  - 注释是否过时、是否冗余、是否易懂（可读性）。
- 忽略明显误报，聚焦真正需要改进处。

### 3. 汇总与反馈

向用户给出结构化结论：
- 整体注释占比与目标对比（达标/不达标）。
- 缺失注释的函数/字段数量与代表样例。
- 一致性问题（占位、描述不匹配）清单。
- 可读性问题清单。
- 如需，按 `references/guidelines.md` 的"好/坏示例"为最关键的若干处**直接补全注释**（先说明再改），改后重跑脚本确认占比提升、问题减少。

## 参考资源

- `references/guidelines.md`：项目注释规范（占比口径、必注位置、一致性/可读性标准、好/坏示例），复核与补注释时遵循。
- `scripts/check_comments.py`：分析器源码，如需调整阈值或正则可读取后修改。

## 注意事项

- 结构性识别（函数/字段判定）基于正则启发式，复杂语法可能误报/漏报，以 AI 复核为准。
- 占比统计按"行"近似（行尾注释计入代码行但记为有注释），合理但不等同于字节级精确比例。
- 补注释不要为凑占比而写废话；以提升可读性与一致性为目標。
